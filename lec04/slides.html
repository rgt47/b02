Question: How do you currently keep track of different versions of your analysis files?

Answer: “I used to save files like ‘analysis_v1.R’, ‘analysis_v2.R’, ‘analysis_final.R’, ‘analysis_final_revised.R’. Within a week I would have dozens of files and no idea which was actually current. Worse, I could not remember what changed between versions or why I made those changes.”

The File Naming Problem

Does this look familiar?

project/

Problems:

  • Which file is current?
  • What changed between versions?
  • Why were changes made?
  • How do you collaborate?

Question: What happens when two team members independently modify the same file and then try to combine their work?

Answer: “Without version control, someone has to manually compare the files line by line and merge the changes by hand. This is tedious and error-prone—you might accidentally overwrite important changes. I once lost two days of work when a collaborator emailed me their version and I saved it over mine, not realizing I had made changes too.”

What is Version Control?

A system that records changes to files over time:

  • Track changes: Every modification is recorded
  • History: See what changed, when, and by whom
  • Revert: Go back to any previous state
  • Branch: Explore alternatives safely
  • Merge: Combine work from multiple people

Note

Think of it as “track changes” for your entire project, but more powerful and designed for code and data analysis.

Question: How is version control different from cloud storage services like Dropbox or Google Drive?

Answer: “Cloud storage syncs files but does not understand them. If two people edit simultaneously, you get a conflict file and must resolve it manually. Version control is designed for this: it tracks line-by-line changes and can often merge automatically. It also captures intent through commit messages—cloud storage only knows a file changed, not why.”

Git: The Version Control Standard

  • Created by Linus Torvalds in 2005 (for Linux development)
  • Distributed: Everyone has the complete history
  • Fast: Most operations are local
  • Branching: Cheap and easy to create branches
  • Now the dominant version control system worldwide

Key insight: Git tracks content, not files

Question: What does it mean that Git is “distributed” and why does that matter for collaborative research?

Answer: “Each collaborator has the entire project history on their computer, not just the latest version. If the central server crashes, no work is lost—anyone can restore the repository from their local copy. It also means you can work offline, making commits and viewing history without internet access, then sync when reconnected.”

Core Git Concepts

  • Repository (repo): A project tracked by Git
  • Commit: A snapshot of your project at a point in time
  • Branch: A parallel version of the repository
  • Merge: Combining branches together
  • Remote: A repository hosted elsewhere (like GitHub)

Question: Why would you create a branch instead of just making changes directly to your main code?

Answer: “Branches let you experiment safely. If I want to try a different statistical model, I create a branch and work there. If the experiment fails, I delete the branch—the main code is untouched. If it succeeds, I merge it in. This is especially important in collaboration: each person works on their own branch, so incomplete work never breaks the shared code.”

Basic Git Workflow

# 1. Check status - what has changed?
git status

# 2. Stage changes - prepare for commit
git add analysis.R
git add data/cleaned_data.csv

# 3. Commit - save snapshot with message
git commit -m "Add initial exploratory analysis"

# 4. View history
git log --oneline

The cycle: Edit → Stage → Commit → Repeat

Question: Why does Git have a separate “staging” step instead of committing all changes at once?

Answer: “Staging lets you group related changes into logical commits. If I fixed a bug and added a new feature, I can stage and commit them separately, making the history clearer. I might also have experimental changes I am not ready to commit—staging lets me be selective. This precision in recording changes makes the project history more useful.”

Writing Good Commit Messages

Good messages explain WHY, not just what:

# Bad - what changed is obvious from the code
git commit -m "Changed threshold"

# Good - explains the reasoning
git commit -m "Increase significance threshold to 0.01 per reviewer request"

# Better - follows conventional format
git commit -m "fix: Correct off-by-one error in bootstrap loop

The loop was running n-1 iterations instead of n, causing
slight underestimation of standard errors. Fixes #23."

Question: How detailed should commit messages be for statistical analysis code?

Answer: “For statistical decisions, I err on the side of more detail. Instead of ‘changed model’, I write ‘Switch from linear to mixed-effects model to account for repeated measures within subjects. ICC = 0.42 suggests substantial clustering.’ Six months later, that context is invaluable. The commit history becomes a lab notebook for your analysis.”

Introduction to GitHub

  • GitHub hosts Git repositories on the internet
  • Provides collaboration features beyond Git:
    • Pull requests for code review
    • Issues for tracking tasks and bugs
    • Actions for automation
    • Project boards for organization

Note

Git is the tool. GitHub is a service that hosts Git repositories and adds collaboration features. Alternatives include GitLab and Bitbucket.

Question: What is the difference between Git and GitHub?

Answer: “Git is software that runs on your computer and tracks changes to files. GitHub is a website that hosts Git repositories online. You can use Git without GitHub—everything works locally. GitHub adds cloud storage, web interface, and collaboration features. The relationship is like R versus RStudio: Git is the engine, GitHub is a interface that makes it easier to use and adds extra features.”

Connecting to GitHub

# Clone an existing repository
git clone https://github.com/username/repo.git

# Add a remote to existing local repo
git remote add origin https://github.com/username/repo.git

# Push local commits to GitHub
git push origin main

# Pull changes from GitHub
git pull origin main

Question: What happens if you try to push but someone else has already pushed changes you do not have?

Answer: “Git rejects the push to prevent you from overwriting their changes. You must first pull their changes, merge them with yours locally, resolve any conflicts if the same lines were modified, and then push the merged result. This ensures no one’s work is ever silently lost—Git forces you to explicitly handle concurrent modifications.”

Collaboration Workflow

  1. Pull latest changes from GitHub
  2. Create a branch for your work
  3. Make changes and commit regularly
  4. Push your branch to GitHub
  5. Open a pull request for review
  6. After approval, merge into main
git pull origin main
git checkout -b feature/add-survival-analysis
# ... make changes ...
git add .
git commit -m "Add Kaplan-Meier survival analysis"
git push origin feature/add-survival-analysis
# Open pull request on GitHub

Question: Why use branches and pull requests instead of everyone committing directly to the main branch?

Answer: “Direct commits to main mean everyone sees work in progress, including bugs and incomplete features. Pull requests create a checkpoint where code is reviewed before merging. For our course projects, this means your teammate can catch errors before they affect the shared analysis. It also creates documentation of who reviewed what, important for reproducibility and accountability.”

What to Track with Git

DO track:

  • Code files (.R, .Rmd, .qmd, .py)
  • Documentation (README.md, .txt)
  • Configuration (renv.lock, .Rprofile)
  • Small data files if necessary

DO NOT track:

  • Large data files (use .gitignore)
  • Sensitive data (PHI, credentials)
  • Generated output (HTML, PDF—usually)
  • Temporary files (.Rhistory, .DS_Store)

Question: How do you share large datasets with collaborators if they should not go in Git?

Answer: “Document where the data lives and how to access it in your README. For institutional data, reference the secure server location. For public data, include download scripts. Some teams use Git LFS (Large File Storage) for versioning large files, or cloud storage with clear naming conventions. The key is making data access reproducible even if the data itself is not in the repository.”

Summary

  1. Version control tracks changes, enables collaboration, provides history
  2. Git is the standard tool: commits, branches, merges
  3. GitHub hosts repositories and adds collaboration features
  4. Workflow: Pull → Branch → Commit → Push → Pull Request → Merge
  5. Track code and documentation, not large data or secrets

# Daily workflow
git status              # See what changed
git add <file>          # Stage changes
git commit -m "msg"     # Commit with message
git push                # Send to remote
git pull                # Get from remote

# Branching
git branch              # List branches
git checkout -b name    # Create and switch to branch
git merge branch        # Merge branch into current

# History
git log --oneline       # Brief history
git diff                # See unstaged changes
git diff --staged       # See staged changes

Question: How do you undo a commit you just made but have not pushed?

Answer: “Use ‘git reset –soft HEAD~1’ to undo the commit but keep your changes staged, or ‘git reset HEAD~1’ to unstage them too but keep the files modified. If you need to completely discard the changes, ‘git reset –hard HEAD~1’ reverts everything—use with caution. Never use reset on commits you have already pushed, as this rewrites history others may have.”

Handling Merge Conflicts

REFERENCE ONLY

When Git cannot automatically merge:

<<<<<<< HEAD
model <- lm(y ~ x1 + x2, data = df)
=======
model <- lm(y ~ x1 + x2 + x3, data = df)
>>>>>>> feature-branch

Resolution steps:

  1. Open the conflicted file
  2. Find the conflict markers (<<<<<<<, =======, >>>>>>>)
  3. Edit to keep the correct version
  4. Remove the conflict markers
  5. Stage and commit the resolved file

Question: How do you decide which version to keep when resolving a merge conflict?

Answer: “Look at what both versions were trying to accomplish. Sometimes one is clearly correct; other times you need to combine them. For analysis code, check with your collaborator to understand their reasoning. The commit messages should explain why changes were made. If unsure, discuss before resolving—a wrong merge can introduce subtle bugs that are hard to trace later.”
