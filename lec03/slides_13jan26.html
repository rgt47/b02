Question: Have you ever had R code that worked perfectly on your computer but failed on a colleague’s machine? What happened?

Answer: “Last semester, my regression analysis ran fine on my laptop but crashed on my advisor’s computer. After hours of debugging, we discovered I was using dplyr 1.1 while she had dplyr 1.0. A function I used had been renamed between versions, and neither of us had documented which version we needed.”

The Dependency Problem

  • R packages update frequently, sometimes with breaking changes
  • Your code depends on specific package versions
  • Different computers have different packages installed
  • System libraries and R versions also vary
  • Result: “Dependency hell” and broken analyses
# This code might work today but fail tomorrow
library(tidyverse)  # Which version?
library(survival)   # Compatible with your R version?

# Six months later: "Error: could not find function..."

Question: Why might package authors make breaking changes that cause existing code to fail?

Answer: “Package authors improve their software over time, fixing bugs and adding features. Sometimes the original design was flawed, and fixing it requires changing how functions work. They face a tradeoff between maintaining backward compatibility forever or improving the package. Most choose improvement, which is good for the ecosystem but challenging for reproducibility.”

What is renv?

  • renv = Reproducible ENVironments for R
  • Creates project-specific package libraries
  • Records exact package versions in a lockfile
  • Allows restoration of identical environments
  • Developed by Posit (formerly RStudio)

Note

renv isolates each project’s packages, so updating packages in one project never affects another project.

Question: How is renv different from simply documenting which packages your code uses in a README file?

Answer: “A README requires manual installation and hopes the versions are still available. renv automates the entire process—it knows which versions you used, where to download them, and how to install them. It also handles dependencies: if package A requires a specific version of package B, renv manages that automatically. Manual documentation cannot capture this complexity reliably.”

Core renv Workflow

Three essential functions:

# 1. Initialize renv in your project
renv::init()

# 2. After installing packages, save the state
renv::snapshot()

# 3. On another machine, restore the environment
renv::restore()

Key files created:

  • renv.lock - JSON file with exact package versions
  • renv/ - Project-specific package library
  • .Rprofile - Activates renv when project opens

Question: When should you run renv::snapshot() during a project?

Answer: “Run snapshot after any package change—installing new packages, updating existing ones, or removing packages you no longer need. I also run it before committing to Git, ensuring the lockfile stays synchronized with my code. Some people snapshot daily as a habit, which catches any inadvertent package changes.”

The renv Lockfile

{
  "R": {
    "Version": "4.4.0",
    "Repositories": [
      {"Name": "CRAN", "URL": "https://cloud.r-project.org"}
    ]
  },
  "Packages": {
    "dplyr": {
      "Package": "dplyr",
      "Version": "1.1.4",
      "Source": "Repository",
      "Repository": "CRAN",
      "Hash": "597b13f9a7f5c2e3f8ab..."
    }
  }
}

Question: Why does the lockfile include a hash for each package?

Answer: “The hash verifies that the installed package matches exactly what was recorded. If someone modified a package after you snapshotted it, or if CRAN replaced a package version, the hash would detect the mismatch. This protects against subtle corruption or tampering that could affect your analysis without obvious errors.”

What renv Cannot Do

renv manages R packages but not:

  • R version itself
  • Operating system
  • System libraries (C/C++ dependencies)
  • Pandoc version (for R Markdown)
  • Other software (Python, databases)

Note

For complete reproducibility, you need something that captures the entire computing environment. Enter Docker.

Question: Can you think of a situation where code might fail even with the correct R packages because of system library differences?

Answer: “Packages that interface with external software often have this problem. For example, the sf package for spatial analysis requires the GDAL, GEOS, and PROJ libraries. If these system libraries are different versions or missing entirely, sf will either fail to install or produce different results. I encountered this when my geospatial analysis gave slightly different coordinates on Linux versus macOS.”

Introduction to Docker

  • Docker creates containers: isolated computing environments
  • A container includes OS, software, libraries, and code
  • Containers run identically on any machine with Docker
  • Like a lightweight virtual machine, but faster

│         Your Computer           │
│  ┌───────────────────────────┐  │
│  │     Docker Container      │  │

Question: How is a Docker container different from a virtual machine?

Answer: “Virtual machines include a complete operating system with its own kernel, making them heavy and slow to start. Containers share the host machine’s kernel and only include the differences from a base image. This makes containers lightweight—they start in seconds and use minimal disk space. For data science, this efficiency means you can quickly spin up reproducible environments without the overhead of full virtualization.”

The Rocker Project

  • Rocker provides Docker images for R
  • Pre-built images with R and common tools
  • Base images you can extend for your needs

Common Rocker images:

Image Contents
rocker/r-ver:4.4.0 R version 4.4.0 only
rocker/rstudio R + RStudio Server
rocker/tidyverse R + RStudio + tidyverse
rocker/verse tidyverse + publishing tools

Question: Why might you choose rocker/r-ver over rocker/tidyverse for a reproducible analysis?

Answer: “Starting with the minimal r-ver image and adding only the packages you need creates a smaller, more focused container. The tidyverse image includes many packages you might not use, increasing image size and potential for conflicts. For reproducibility, it is better to explicitly install and document every dependency rather than rely on a large pre-built image that might change over time.”

Creating a Dockerfile

# Start from R 4.4.0
FROM rocker/r-ver:4.4.0

# Set working directory
WORKDIR /workspace

# Install renv
RUN R -e "install.packages('renv', repos='https://cloud.r-project.org')"

# Copy lockfile and restore packages
COPY renv.lock /workspace/renv.lock
RUN R -e "renv::restore()"

# Copy analysis files
COPY . /workspace

# Default command
CMD ["R"]

Question: Why do we copy and restore the renv.lock file before copying the rest of our analysis files?

Answer: “Docker caches each layer, rebuilding only when something changes. If we copy all files first, any change to our analysis code would invalidate the cache and force package reinstallation. By copying the lockfile separately, packages only reinstall when dependencies change. This optimization dramatically speeds up rebuilds during development.”

Running Docker Containers

# Build the image
docker build -t my-analysis:v1 .

# Run interactively with local files mounted
docker run --rm -it \
  -v "$(pwd):/workspace" \
  -w /workspace \
  my-analysis:v1 \
  /bin/bash

Key flags:

  • --rm — Remove container when it exits
  • -it — Interactive terminal
  • -v — Mount local directory into container
  • -w — Set working directory

Question: What happens to files you create inside a container if you do not use the -v volume mount?

Answer: “Without a volume mount, files exist only inside the container’s filesystem. When the container stops, especially with –rm, those files vanish completely. This is actually a feature for reproducibility—containers start fresh every time—but during development you need mounts to preserve your work. Always mount your working directory when doing interactive analysis.”

Combining renv and Docker

Best practice workflow:

  1. Develop analysis locally with renv
  2. Run renv::snapshot() to capture packages
  3. Create Dockerfile using renv.lock
  4. Build and test Docker image
  5. Share image via DockerHub or registry
  6. Collaborators pull image and run analysis

Note

Docker guarantees the OS and R version. renv guarantees the packages. Together, they provide complete reproducibility.

Question: In what order should you commit files when setting up a new reproducible project with renv and Docker?

Answer: “First commit the basic project structure and renv.lock after initializing renv. This lets collaborators restore packages immediately. Add the Dockerfile once your analysis stabilizes—you do not want to rebuild images constantly during early development. Finally, document the workflow in your README so others know whether to use renv::restore() locally or pull your Docker image.”

Summary

  1. The problem: R projects break due to package version mismatches
  2. renv: Captures exact package versions in a lockfile
  3. Docker: Containerizes the entire computing environment
  4. Together: Complete, portable reproducibility
  5. Workflow: Develop with renv, deploy with Docker

renv Troubleshooting

REFERENCE ONLY

Common issues and solutions:

# Check status of renv
renv::status()

# Update renv itself
renv::upgrade()

# If restore fails, try cleaning first
renv::clean()
renv::restore()

# See what packages are different from lockfile
renv::status()

# Install specific package version
renv::install("dplyr@1.1.0")

Question: What should you do if renv::restore() fails with a message about unavailable packages?

Answer: “First check if the package was removed from CRAN—this happens occasionally with problematic packages. Try the CRAN archive or the package’s GitHub repository as alternative sources. You can also use renv::install() with a specific URL. If the package is truly unavailable, you may need to find an alternative and update your code.”

Question: How do you share a Docker image with collaborators who do not have DockerHub accounts?

Answer: “You can save an image to a file with ‘docker save -o myimage.tar myimage:tag’ and share that file directly. Recipients load it with ‘docker load -i myimage.tar’. This is useful for restricted environments or very large images where upload bandwidth is limited. However, DockerHub or a private registry is preferred for ongoing collaboration.”
