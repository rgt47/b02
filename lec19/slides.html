Part I: Reproducible Research

Reproducibility: Core Definitions

  • Reproducibility: Same data + same code = same results
  • Replicability: New data + same methods = consistent findings
  • Transparency: Complete documentation of analytical decisions

Five components of a reproducible analysis:

  1. Data management – raw data preservation, clear provenance
  2. Code organization – modular, well-documented scripts
  3. Environment capture – package versions, system dependencies
  4. Documentation – README files, analysis narratives
  5. Version control – complete history of changes

Question: A collaborator runs your R script from six months ago and gets different regression coefficients. The data file is identical. What are the three most likely causes?

Answer: (1) Package versions changed – a function’s default arguments or internal behavior may have been updated. (2) R version differs – floating-point handling or random number generation can vary across versions. (3) A seed was not set for any stochastic step in the pipeline, such as imputation or cross-validation splits.

Question: Why is renv alone insufficient for full reproducibility?

Answer: renv locks R package versions but cannot control the R version itself, operating system, or system-level C/C++ libraries. Packages like sf depend on system libraries (GDAL, GEOS) that may differ across machines. Docker complements renv by containerizing the entire computing environment, guaranteeing identical behavior regardless of the host machine.

Part II: renv and Docker

renv: Package Version Control

Three essential functions:

renv::init()       # Initialize: create project library + lockfile
renv::snapshot()   # Save current package versions to renv.lock
renv::restore()    # Install exact versions from renv.lock

Key files created:

  • renv.lock – JSON file with exact package versions and hashes
  • renv/ – project-specific package library
  • .Rprofile – auto-activates renv when project opens

Question: You install a new package with install.packages("glmnet") inside an renv project. What must you do before committing to Git?

Answer: Run renv::snapshot() to update renv.lock with the new package and its dependencies. Without this step, the lockfile will be out of sync with your code, and a collaborator running renv::restore() will not get glmnet installed. You can verify synchronization with renv::status().

Docker: Environment Containerization

FROM rocker/r-ver:4.4.0

RUN apt-get update && apt-get install -y \
    libcurl4-openssl-dev libssl-dev libxml2-dev

WORKDIR /workspace

RUN R -e "install.packages('renv', repos='https://cloud.r-project.org')"

COPY renv.lock renv.lock
COPY renv/activate.R renv/activate.R
RUN R -e "renv::restore()"

CMD ["/bin/bash"]
docker build -t myimage:v1 .                          # Build
docker run --rm -it -v "$(pwd):/workspace" myimage:v1  # Run
docker push username/myimage:v1                        # Share

Question: Why does the Dockerfile copy renv.lock before copying the rest of the analysis files?

Answer: Docker caches each layer and only rebuilds layers that change. If all files are copied first, any edit to analysis code invalidates the cache and forces a full package reinstallation. Copying the lockfile separately ensures packages are only reinstalled when dependencies actually change, reducing rebuild time from minutes to seconds during development.

Part III: Version Control

Git and GitHub

Core workflow: Edit – Stage – Commit – Push

git status                                    # What changed?
git add analysis.R                            # Stage specific files
git commit -m "Add species interaction model" # Snapshot with message
git push origin main                          # Send to GitHub

Collaboration workflow:

  1. git pull origin main – get latest changes
  2. git checkout -b feature/survival-analysis – create branch
  3. Make changes, commit regularly
  4. git push origin feature/survival-analysis – push branch
  5. Open pull request on GitHub for code review
  6. After approval, merge into main

Question: Your teammate pushed changes to main while you were working on a branch. You try to merge your branch and Git reports a conflict. What do you do?

Answer: Open the conflicted file and find the conflict markers (<<<<<<<, =======, >>>>>>>). The section above ======= is your version; below is your teammate’s. Edit the file to keep the correct version (or combine both), remove all conflict markers, then git add the resolved file and git commit. Always discuss with your teammate before resolving conflicts in shared analysis code to avoid introducing subtle errors.

Part IV: Statistical Analysis Plans

Elements of a Statistical Analysis Plan

A Statistical Analysis Plan (SAP) is written before conducting the analysis. It specifies:

Section Contents
Introduction Research questions, hypotheses, literature context
Data description Source, population, key variables
Statistical methods Descriptive stats, primary analysis, sensitivity
Missing data Strategy (complete case, imputation, justification)
Results presentation Table shells, planned figures
Sensitivity analyses Robustness checks, alternative specifications

Note

The SAP prevents data dredging, documents analytical intentions, and serves as a contract between team members about what will be done.

Question: Why should table shells be included in the analysis plan rather than created after the analysis is complete?

Answer: Table shells force you to think through exactly what you will report before seeing results. They identify gaps in your variable list – if you cannot fill a cell, you may be missing a required measurement. They also prevent post-hoc addition of favorable comparisons. In clinical trials, table shells are required by FDA guidance (ICH E9). For course projects, they ensure your team agrees on deliverables before dividing work.

Part V: Testing Data Analysis Workflows

Types of Tests for Data Science

Test Type What It Checks Example
Unit tests Individual functions clean_penguins() removes NAs
Data validation Data quality All body masses > 0, species valid
Integration Full pipeline Scripts 01-04 run without error
Reproducibility Determinism Same seed yields same bootstrap CI 
test_that("clean_penguins removes rows with missing values", {
  test_data <- data.frame(
    species = c("Adelie", "Gentoo", "Chinstrap"),
    bill_length = c(39.1, NA, 46.5),
    body_mass = c(3750, 4500, NA)
  )
  cleaned <- clean_penguins(test_data)

  expect_equal(nrow(cleaned), 1)
  expect_equal(cleaned$species, "Adelie")
  expect_false(any(is.na(cleaned)))
})

Question: What is the difference between expect_equal() and expect_identical() in testthat, and when would you use each?

Answer: expect_equal() allows a small numerical tolerance (default 1.5e-8), appropriate for floating-point comparisons such as regression coefficients or computed means. expect_identical() requires an exact bitwise match, appropriate for strings, integers, and logical values where tolerance is meaningless. Use expect_equal() for model outputs; use expect_identical() for checking that a factor level is exactly "Adelie" rather than "adelie".

Part VI: Regression and Model Diagnostics

Linear Regression: From Simple to Species-Aware

\[\text{body_mass}_i = \beta_0 + \beta_1 \cdot \text{flipper_length}_i + \epsilon_i\]

Model building strategy (sequential):

Model Predictors R-squared CV RMSE (g)
Simple Flipper length 0.759 ~390
Multiple Flipper + bill length + bill depth 0.779 ~380
Species-aware + species 0.868 ~290

Interpretation of the simple model:

  • Intercept: -5781 g (extrapolation, not meaningful)
  • Slope: 49.7 g per mm of flipper length
  • Each additional mm of flipper length is associated with ~50 g of body mass

Question: The multiple regression model (without species) shows a negative coefficient for bill depth. The bivariate correlation between bill depth and body mass is positive. How is this possible?

Answer: This is Simpson’s Paradox. Gentoo penguins are the largest species but have shallow bills, while Adelie penguins have deep bills but smaller bodies. When species is omitted, the model conflates between-species differences with the within-species relationship. The negative coefficient reflects the confounded overall trend. Adding species to the model resolves the paradox and reveals the expected positive within-species association between bill depth and body mass.

Model Diagnostics and Cross-Validation

Four diagnostic plots (from plot(model)):

  1. Residuals vs. Fitted – linearity and constant variance
  2. Q-Q Plot – normality of residuals
  3. Scale-Location – homoscedasticity
  4. Residuals vs. Leverage – influential observations

Multicollinearity: Variance Inflation Factor (VIF)

  • VIF > 5 indicates concerning multicollinearity
  • VIF > 10 indicates severe multicollinearity

Cross-validation provides honest performance estimates:

library(caret)
set.seed(42)
train_control <- trainControl(method = "cv", number = 10)
cv_model <- train(body_mass_g ~ ., data = penguins_clean,
                  method = "lm", trControl = train_control)

Question: Your training R-squared is 0.92 but your 10-fold cross-validated R-squared is 0.71. What does this discrepancy suggest, and what would you do?

Answer: A large gap between training and CV performance indicates overfitting – the model has learned noise in the training data that does not generalize. Potential remedies: (1) Reduce model complexity by removing weak predictors or using regularization (e.g., elastic net). (2) Increase sample size if possible. (3) Use feature selection guided by domain knowledge rather than automated stepwise methods. The CV estimate is the honest one; the training R-squared is optimistically biased.

Part VII: Machine Learning and Classification

Predicting MCI to AD Conversion

The clinical problem: Not all MCI patients progress to Alzheimer’s disease. Identifying who will convert enables targeted treatment planning, clinical trial enrollment, and family counseling.

Grassi et al. (2019) approach:

  • Cohort: MCI subjects from ADNI with 3+ years follow-up
  • Outcome: Binary (converter vs. stable within 3 years)
  • Features: Baseline clinical and cognitive data only
  • Result: AUROC = 0.88 using ensemble of 13 algorithms

Top predictors (ranked by individual AUROC):

Rank Feature AUROC
1 ADAS-Cog (PC1) 0.809
2 RAVLT Immediate 0.777
3 FAQ 0.777
4 LDELTOTAL 0.770
5 CDRSB 0.697

Question: Grassi et al. intentionally excluded imaging (MRI, PET) and genetic (APOE4) features. Why might excluding the most accurate biomarkers be a deliberate methodological choice?

Answer: The goal was clinical translatability. MRI and PET scans are expensive, require specialized equipment, and are not available in many community clinics. APOE4 genotyping raises ethical concerns about genetic discrimination. By restricting features to standard neuropsychological assessments (MMSE, ADAS, RAVLT) and clinical scales (CDR-SB, FAQ), the resulting model can be deployed in any clinical setting with a trained assessor. Achieving AUROC = 0.88 with only clinical features demonstrates that expensive biomarkers are not always necessary for clinically useful prediction.

Evaluation Metrics for Classification

Metric Formula Interpretation
Sensitivity TP / (TP + FN) Proportion of true converters detected
Specificity TN / (TN + FP) Proportion of true stable identified
PPV TP / (TP + FP) Of predicted converters, how many are true
NPV TN / (TN + FN) Of predicted stable, how many are true
AUROC Area under ROC curve Overall discrimination ability

ROC curve: Plot of sensitivity vs. (1 - specificity) across all classification thresholds. A perfect classifier has AUROC = 1.0; random guessing gives AUROC = 0.5.

library(pROC)
roc_obj <- roc(test_data$converter, predictions)
plot(roc_obj)
auc(roc_obj)
coords(roc_obj, "best",
       ret = c("threshold", "sensitivity", "specificity"))

Question: In the ADNI prediction task, the conversion rate is approximately 25%. If you built a model that always predicted ‘stable’ for every patient, what would the sensitivity, specificity, and accuracy be?

Answer: Sensitivity = 0% (no converters detected), specificity = 100% (all stable correctly labeled), and accuracy = 75% (since 75% of patients are stable). This illustrates why accuracy is misleading for imbalanced outcomes. A model that never detects the outcome of interest is clinically useless despite appearing 75% ‘accurate.’ This is why AUROC, sensitivity, and specificity are the appropriate metrics for classification with class imbalance.

Four Datasets, Four Design Contexts

Common analytical thread across all projects:

  1. Write SAP before analyzing data
  2. Explore data with descriptive statistics and visualizations
  3. Fit appropriate models with proper diagnostics
  4. Validate results (cross-validation, sensitivity analyses)
  5. Present in reproducible compendium (rrtools + renv + Git)

Question: What is the fundamental difference between the analytical approach for Project 4 (Licorice Gargle RCT) and Projects 1–3 (observational data)?

Answer: In an RCT, randomization ensures that treatment groups are balanced on both observed and unobserved confounders at baseline, permitting causal inference. The primary analysis follows intention-to-treat (ITT): subjects are analyzed in the group to which they were randomized regardless of compliance. In observational studies (Projects 1–3), confounding must be addressed through statistical adjustment (regression, matching, stratification) and causal claims are limited. The policing data (P3) is especially vulnerable to unmeasured confounding because officer decisions and departmental policies vary in ways that cannot be fully captured in the data.

Question: For the ADNI project, why is a site-independent train/test split preferable to a random split of individual subjects?

Answer: Subjects within the same site share unmeasured characteristics: the same clinicians administer cognitive tests, the same MRI scanner acquires images, and local referral patterns affect patient demographics. A random split would leak these site-level correlations into both training and test sets, producing optimistically biased performance estimates. A site-independent split simulates real-world generalization: will the model work at a clinic that was not used for training? This is the clinically relevant question.

Question: A reviewer asks you to change your primary regression model from linear to mixed-effects. What steps in this workflow are affected, and in what order should you address them?

Answer: (1) Update the SAP to document and justify the change. (2) Install lme4 and run renv::snapshot() to record the new dependency. (3) Modify your analysis script to fit the mixed model. (4) Update tests to reflect the new model class (expect_s4_class for lmer objects). (5) Re-run all tests to confirm nothing else broke. (6) Update the report narrative and tables. (7) Commit all changes with a descriptive message explaining why the model changed. (8) Rebuild the Docker image if sharing via container.
